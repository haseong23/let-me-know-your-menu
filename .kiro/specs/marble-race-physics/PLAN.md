# 구슬 레이스 개선 계획

참고 대상: <https://lazygyu.github.io/roulette/>

> **상태: B안으로 구현 완료(v9.84).** 아래는 그 결정에 이른 근거이며, 실제로 구현된 것과 다른 부분이 있어 그 자리에 표시해 뒀다.
>
> 사용자가 확정한 범위 변경:
> - **소리·카메라 연출(P2)은 하지 않는다.** 카메라는 기존 선두 추적만 유지한다.
> - **길이는 늘어나도 된다.** 물리라 시간 제어가 어렵다는 점을 받아들였다 — 실측 14~21초.
> - **길은 세 가지뿐이다** — 1자길 · 지그재그길 · 깔때기길. 속도를 흩는 일은 장애물이 한다.
> - **마찰이 없다.** 에너지를 잃는 경로는 반발(벽·장애물·구슬끼리)뿐이다.
> - **확률 정책은 사다리타기·돌림판에만 적용한다.** 레이스는 승자를 미리 뽑지 않고 물리가 정하므로
>   2절의 '이름을 1등 구슬에 앉히는' 방식은 **쓰지 않았다** — 이름은 구슬 번호에 그냥 붙고,
>   출발 x 가 각자 독립 난수라 번호에 의미가 없어 그 자체로 균등하다. 결과적으로 3절의 누출
>   대비(출발 깔때기)는 그대로 필요하고 그대로 넣었다. [제외]는 네 게임 모두에 적용된다.

## 1. 왜 조악한가 — 격차의 정체

우리 구현(`index.html` 1782~1893행 순수 함수 · 3027~3260행 렌더)과 참고 대상의 차이는 "완성도"가 아니라 **작동 원리**다.

| | lazygyu/roulette | 지금 우리 |
| --- | --- | --- |
| 움직임의 출처 | 물리 시뮬레이션(중력·충돌·마찰) | `raceXY(course, p)` — **모든 구슬이 같은 사인 곡선** 위를 탄다 |
| 구슬끼리 | 실제로 부딪히고 밀린다 | 겹친 자리에 흰 테두리만 남기고 통과 |
| 코스 | 못·깔때기·회전 장애물·좁은 문 | 진폭 40~110의 사인 12구간, 그게 전부 |
| 속도 | 낙하 가속·반발로 매 순간 다름 | 구간별 속도 편차 하나로 흉내 |
| 벽 | 충돌 지오메트리 | ±17px **장식 외곽선** |
| 순위 | 창발 | `order = [wi].concat(rest)` 로 미리 확정 |
| 카메라 | 선두 추적 + 확대 | 선두 추적(등속) |
| 소리 | 있음 | 없음 |

**핵심은 한 줄이다 — 우리 구슬은 서로를 모른다.** 24개가 같은 곡선을 타고 내려오면서 속도만 다르니, 화면에는 "세로로 늘어선 점들이 나란히 흐르는 것"만 남는다. 참고 대상이 재미있는 이유는 **구슬이 서로 부딪혀 예측이 안 되기 때문**이고, 그건 연출로 흉내 낼 수 있는 종류가 아니다.

## 2. 그동안 물리 엔진을 접었던 이유와, 그게 왜 더는 유효하지 않은가

이전 스펙의 결정 기록 4번은 물리 엔진을 두 가지 이유로 기각했다.

1. **비용** — 직접 구현 11~16일, 참고 대상 수준까지 24~35일.
2. **확률 정책과 충돌** — 물리가 결과를 만들면 `soft`(직전 섬긴 분 1/3) 가중치를 걸 지점이 없다. 살리려면 원하는 승자가 나올 때까지 다시 돌리는 **거부 표집**이 필요하고, 그러면 게임 앞에 1.2~3.5초의 설명할 수 없는 로딩이 붙는다.

**2번은 해소된다. 순서를 뒤집으면 된다.**

```
① 정책대로 당첨자 W 를 뽑는다                    (지금과 동일 — gamePickWinner)
② 익명 구슬 n 개로 물리 시뮬레이션을 헤드리스로 1회 돌린다
③ 1등으로 들어온 구슬 자리에 W 를 앉히고, 나머지 이름을 남은 자리에 섞어 넣는다
④ 같은 시드·같은 고정 스텝으로 다시 돌리며 화면에 그린다 → ②와 글자 하나 안 틀리게 재현된다
```

거부 표집이 아니다. **시뮬레이션은 정확히 한 번**이고, 이름↔구슬 대응만 결과를 보고 정한다. 구슬은 반지름·질량·반발계수가 모두 같아서 어떤 대응이든 물리적으로 구별되지 않는다. 물리는 100% 진짜이고 확률 정책도 100% 지켜진다.

**1번(비용)도 이 트릭 덕분에 줄어든다.** 11~16일 추정은 거부 표집 루프와 그 성능 최적화를 포함한 값이었다. 아래 4절의 범위로 다시 잡으면 **6.5~9일**이다.

### 여기서 반드시 같이 막아야 하는 것 — R6와 같은 종류의 누출

③에서 W 를 "1등 구슬의 자리"에 앉히므로, **코스가 특정 출발 레인을 구조적으로 유리하게 만들면 출발 그리드가 곧 답이 된다.** 돌림판에서 라벨 기울기가 답이었던 것과 정확히 같은 사고다. 두 가지로 막는다.

- 코스를 매 판 시드로 새로 만든다(레인 유불리가 판마다 달라진다).
- 출발을 레인이 아니라 **깔때기(hopper)** 로 한다 — 구슬을 한 곳에 쏟아 물리로 순서가 섞인 뒤 본선이 시작된다. 출발선의 좌우 위치가 정보를 갖지 않게 된다.

이 둘은 선택이 아니라 **요구사항**이다.

## 3. 두 가지 길

| | A. 연출만 강화 | **B. 자체 물리 (추천)** |
| --- | --- | --- |
| 내용 | 이전 스펙의 R7~R10 — 렌더 공간 추돌·장애물 통과 연출·소리·카메라 | 작은 2D 강체 솔버를 직접 짜서 실제로 굴린다 |
| 구슬끼리 | 겹치면 밀어내고 스프링으로 복귀(순위 불변) | 진짜 충돌 |
| 코스 | 사인 곡선 + 장애물 장식 | 못밭·깔때기·경사·회전 장애물·좁은 문 |
| 순위 | 미리 확정 | 창발(이름만 사후 대응) |
| "여러 판 보면 장애물이 결과를 안 바꾼다는 걸 알아챈다" | 남는 한계 | **없어진다** |
| 비용 | 4.5~7.5일 | 6.5~9일 |
| 새 라이브러리 | 없음 | 없음 |

**B를 추천한다.** 1.5일 차이로 근본 원인이 사라진다. A는 "같은 곡선을 타는 구슬들"이라는 구조를 그대로 두고 그 위에 장식을 얹는 것이라, 참고 대상과의 격차가 줄긴 해도 성격은 안 바뀐다.

B가 부담스러우면 A로 내려갈 수 있고, 그때도 3절의 누출 방지와 아래 P2(소리·카메라)는 그대로 쓴다.

## 4. B의 범위 — 4단계

### P0 · 시뮬레이션 코어 (2~3일)

- 고정 시간 스텝(dt=1/240, 프레임당 4 서브스텝)의 준암시적 오일러. 가변 dt 를 쓰면 재현이 깨진다.
- 원-원 충돌: 위치 보정 + 반발계수 임펄스. 원-정적선분/원-정적원 충돌.
- 광역 단계: 세로로 긴 통이라 **y 정렬 후 sweep** 하나면 24개에 충분하다.
- 터널링 방지: 서브스텝 + 속도 상한. 필요하면 가장 빠른 구슬만 스윕 판정.
- **전부 순수 함수로 마커 블록 안에** 넣는다. 난수는 시드 인자로만 받는다. 지금 레이스 함수 6개가 이미 그 자리에 있어서 형식이 그대로 맞는다.
- 이름 사후 대응(2절 ①~④) 배선.

### P1 · 코스 (2~3일)

- 맵을 데이터로 기술한다 — 선분·원·회전 선분의 목록. 시드로 구간을 조립한다.
- 구간 종류 최소 4가지: **깔때기(출발)** · **못밭** · **지그재그 경사** · **회전 장애물**. 마지막에 **좁은 문**으로 몰아 결승 직전 긴장을 만든다.
- 회전 장애물은 각도가 시간의 함수라 정적 캐시에 넣지 않고 매 프레임 그린다.
- **캔버스 4096px 제한이 사라진다.** 지금은 코스 전체(2400×1.5=3600px)를 한 장에 미리 그려서 여유가 496px뿐인데, 물리 코스는 화면에 보이는 구간(≈440 논리 px)만 매 프레임 그리면 된다. 정적 도형 50개 그리기는 프레임 예산에 영향이 없다.

### P2 · 감각 (1.5~2일)

- **소리** — WebAudio 합성만(에셋 0바이트). 충돌 세기에 비례한 짧은 클릭, 결승 팡파레. 동시 발음 수 상한. 명시적 음소거 토글 + 기기별 저장. `AudioContext` 는 게임을 시작시킨 제스처 안에서 만든다(iOS).
- **카메라** — 선두 추적에 더해 결승 직전 확대, 선두 교체 시 짧은 이동, 충돌 시 미세 흔들림. 기존 `RACE_CAM`(0.42) · `RACE_CAM_PAD`(24) 클램프를 확장해서 쓴다.
- 충돌 시 구슬 찌그러짐(스케일) 같은 값싼 표현.

### P3 · 다듬기 (1일)

- 18~22초 맞추기. 물리라 소요 시간이 창발이므로 **헤드리스 1회를 재고, 범위를 벗어나거나 역전이 3회 미만이면 시드를 바꿔 다시 잰다.** 1회가 10~40ms 라 몇 번 돌려도 사용자는 못 느낀다(거부 표집이 아니다 — 승자가 아니라 소요 시간·역전 횟수만 본다).
- `lessMotion()` 이면 재생을 건너뛰고 결과로 직행(기존 처방 유지).
- HUD·범례·`⏭ 건너뛰기`·중단 시 정리는 지금 구조를 그대로 쓴다.

## 5. 결정론 — 이게 이 계획의 전제다

②와 ④가 **정확히** 같은 결과를 내야 한다. 안 그러면 이름이 붙은 구슬이 1등을 못 한다.

- 고정 dt. `Math.random` 은 스텝 안에 없다(시드 PRNG 로 맵 생성 때만).
- 반복 순서 고정(객체 순회 대신 배열 인덱스).
- **`Math.sin`·`cos`·`pow` 를 스텝 안에서 쓰지 않는다.** IEEE754는 사칙연산과 `sqrt` 만 정확한 반올림을 보장하고 초월함수는 엔진마다 다르다. 회전 장애물의 각도처럼 필요한 값은 맵 생성 단계에서 미리 계산해 표로 넣는다.
- 다만 **브라우저 간** 결정론은 필요 없다. ②와 ④가 같은 세션·같은 엔진에서 도니까. Node 테스트에서는 골든값이 아니라 성질(같은 시드 2회 → 동일 · 터널링 0 · 소요 시간 범위 · 역전 횟수)을 검증한다.

## 6. 검증

기존 마커 블록 + `node --test` 를 그대로 쓴다(현재 38개 통과). 추가할 것:

| 테스트 | 무엇을 막는가 |
| --- | --- |
| 같은 시드로 2회 돌리면 도착 순서·시각이 완전히 같다 | 재생과 헤드리스가 어긋나 이름이 헛도는 사고 |
| 어떤 구슬도 벽을 통과하지 않는다(전 스텝 검사) | 터널링 |
| 소요 시간이 18~22초 안이다(시드 200개) | P3 예산 |
| 역전이 3회 이상이다(시드 200개) | 밋밋한 판 |
| 이름 대응 후 W 가 1등이다(시드 200개) | 2절 ③의 핵심 |
| 구슬 24개에서 헤드리스 1회가 60ms 이하다 | 시드 재시도가 사용자에게 보이는 것 |
| 정책 `soft` 에서 직전 섬긴 분의 당첨 빈도가 1/3 로 수렴한다 | 물리 도입이 확률을 흔들지 않았음 |

사람이 밟는 QA 는 TC163부터(TC158~TC162 는 그 앞의 UI 수정이 썼다).

## 7. 안 하는 것

- 물리 라이브러리(matter.js 등) 도입. 단일 파일·의존성 0 원칙 유지.
- 참고 대상의 스킬·아이템 시스템. 목표는 "같은 장르로 읽히는 것"이지 기능 대응이 아니다.
- 서버에서 결과 뽑기. 개발자 도구로 DOM·메모리를 열면 답이 보이는 한계는 그대로 남는다(다른 세 게임과 동일).
- 결과의 구속력 변경. `[확정하기]` 전에는 서버에 아무것도 안 쓴다.

## 8. 먼저 정해주셔야 하는 것

1. **A인가 B인가.** 추천은 B(자체 물리).
2. **일정.** B는 6.5~9일이고 P0→P3 순으로 각 단계 끝에서 배포 가능한 상태가 된다. P0만 하고 멈춰도 "구슬이 실제로 부딪힌다"는 얻는다.
3. **길이.** 지금 20초를 유지할지. 코스가 다양해지면 25~30초도 견딜 만한데, 그건 "다 같이 폰을 보는 시간"이 그만큼 길어진다는 뜻이다.
