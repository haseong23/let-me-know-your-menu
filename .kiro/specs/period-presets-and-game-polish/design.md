# Design — 기간 프리셋 정리와 게임 마무리 다듬기

## 개요

이 스펙은 새 기능을 붙이지 않고 이미 동작하는 영역의 결함을 고친다. 대시보드 기간 프리셋의 의미를 바로잡고(`이번주` 월요일 시작 · `최근3개월` 달력 3개월) 6개 칩이 320px 폰에서 한 줄에 들어가게 하며(R1~R3), 손가락 룰렛의 인원 불일치를 진행 전에 묻고 가운데 멘트의 가독성을 확보하고(R4~R5), 돌림판 라벨 기울기로 당첨자가 새는 결정론적 정보 누출을 막는다(R6). 배포 위생을 함께 지키고(R11), 열린 섬김 화면의 `내 주문`과 `현황 n잔`을 중복 제거와 함께 한 화면으로 합치고(R12), 142개 `font-size` 선언의 감사 결과 중 **서체 결함 · 고아값 · 타입 스케일 도입**까지를 처리한다(R13).

모든 결정은 같은 제약 아래에서 내려진다. 코드는 단일 파일 `index.html`에 머물고, 새 프론트엔드 라이브러리와 `package.json` · 빌드 단계는 도입하지 않으며, 파일 분리도 하지 않는다. 테스트 가능한 로직은 `/* @test-export:start */ … /* @test-export:end */` 마커 블록 안의 순수 함수로만 추출되고 난수는 인자로 받는다.

또한 순서 제약이 하나 있다. R3이 `.dash-filter .tab`의 최종 값을 정하고, R13의 타입 스케일은 그 값을 되돌리지 않고 흡수한다.

# A. 대시보드 기간 프리셋 (R1~R3)

## A.0 순수 함수를 어디에 둘 것인가 — 추출기를 여러 블록으로 확장한다

R1·R2는 달·해 경계에서 틀리기 쉬운 날짜 산수다. R11-6·R11-7이 테스트를 요구하고, R2-2·R2-3(1월·2월 경계)은 그 자체가 검증 대상이다. 그런데 현재 추출기는 **블록을 하나만** 읽는다.

```js
const afterStart = source.split(MARK_START);   // [1] 만 쓴다 → 첫 블록만
const body = afterStart[1].split(MARK_END);
```

블록이 하나뿐이면 날짜 헬퍼가 유일한 호출부(`presetRange`, 3613행)에서 **2,000행 떨어진** 게임 블록(1565행) 안에 살게 된다. 그 대신 **추출기가 모든 마커 블록을 파일 순서대로 이어 붙이도록** 바꾼다.

```js
// 마커 블록은 여러 개일 수 있다 — 도메인이 다른 순수 함수를 한 블록에 몰아넣으면
// 그 블록이 잡동사니 서랍이 되고, 함수가 호출부에서 수천 행 떨어진다.
// 파일에 나온 순서대로 이어 붙여 한 번에 평가한다(선언 이름은 서로 겹치지 않아야 한다).
function extractBlock(source) {
  const parts = source.split(MARK_START);
  assert.ok(parts.length >= 2, `${ERR_NO_START} …`);
  return parts.slice(1).map((seg, i) => {
    const body = seg.split(MARK_END);
    assert.ok(body.length >= 2, `${ERR_NO_END} … (${i + 1}번째 블록)`);
    return body[0].replace(/^[^\n]*\n/, "");   // 마커 첫 줄 제거
  }).join("\n");
}
```

**이 변경으로 잃는 것이 없음을 확인한다.** 기존 실패 모드 네 가지(시작 마커 없음 · 종료 마커 없음 · 평가 실패 · 심볼 누락)는 그대로 살아 있다. 특히 "마커가 지워져 테스트가 조용히 통과"하는 사고는 `REQUIRED` 목록이 막는데, 새 심볼을 그 목록에 추가하므로 **블록 하나를 통째로 지우면 심볼 누락으로 터진다.** "시작 마커는 한 줄이어야 한다" 테스트는 모든 블록을 검사하도록 함께 넓힌다.

새 블록의 자리는 `shiftDate` 바로 위(3605행 근처)다.

## A.1 이번주는 월요일에 시작한다 (R1)

```js
/* @test-export:start */  ← 두 번째 마커 블록(대시보드 기간)
// 기준일이 속한 주의 월요일까지 되돌릴 일수. getUTCDay() 는 일요일이 0 이라
// +6 %7 로 월(1)→0 · 화(2)→1 · … · 일(0)→6 이 된다.
function weekBackDays(ds){ return (new Date(ds + "T00:00:00Z").getUTCDay() + 6) % 7; }

// (이번 달 − 2)월 1일. 1월 → 전년 11월, 2월 → 전년 12월.
function q3Start(y, m){ const mm = m - 2; return mm <= 0 ? [y - 1, mm + 12] : [y, mm]; }
/* @test-export:end */
```

호출부:

```js
// 월요일 시작 — 사용자 지시로 정한 값이다. 예전 주석의 근거("교회 한 주가 주일부터라
// 달력과 감각이 맞는다")는 그 지시로 대체됐다. 끝은 그대로 오늘이다: '이번달'·'올해'가
// 이미 오늘로 자르고 있고, 서버 _dash_range 가 미래 종료일을 오늘로 클램프하므로
// 화면에 일요일까지 적고 서버는 오늘까지 집계하는 어긋남을 애초에 만들지 않는다.
case "week":    return [shiftDate(t, -weekBackDays(t)), t];
```

```js
// 달력 3개월 — '이번 달을 포함한 최근 세 달'이고 첫날은 항상 1일이다.
// 예전에는 오늘 기준 90일 롤링이라 '지난달'과 겹치는 구간이 애매했다.
case "q3":      { const [yy, mm] = q3Start(y, m); return [p(yy, mm, 1), t]; }
```

**검증되는 성질** — `dashSpanDays()`는 `week`에서 1~7을 내므로 레거시 폴백의 31일 상한에 안 걸린다(R1-10). `q3`는 최대 92일이라 서버의 366일 상한에 안 걸린다(R2-6). 라벨 `이번주`는 유지(R1-8), `q3` 키와 계산은 라벨을 줄여도 그대로(R2-9). `.tab.on` 판정은 `dashFrom===r[0] && dashTo===r[1]` 비교라 그대로 맞는다(R2-10).

## A.2 프리셋 칩 6개를 320px에 넣는다 (R3)

**요구사항의 폭 예산을 정정한다.** R3은 가용 폭을 `320 − 28 = 292px`로 잡았으나 `#app`의 좌우 패딩이 빠졌다. `@media (max-width:360px)`에서 `#app { padding-left/right: 12px }`이므로 320px 화면의 실제 가용 폭은

```
320 − (#app 12×2) − (.dash-ctl 14×2) = 320 − 24 − 28 = 268px
```

이다. **목표는 292px이 아니라 268px이다.**

한글 글리프의 어드밴스는 1em이므로 12px에서 3글자 = 36px이다. 라벨 글자 폭 합계는 `이번주 36 + 지난달 36 + 이번달 36 + 3개월 31 + 올해 24 + 작년 24 ≈ 187px`.

| 티어 | 좌우 패딩 | gap | 합계 | 가용 | 판정 |
| --- | --- | --- | --- | --- | --- |
| 361~440px | 7px | 3px | 187 + 84 + 15 = **286** | 305 (@361) | ✅ |
| ~360px | 5px | 2px | 187 + 60 + 10 = **257** | 308 (@360) · **268 (@320)** | ✅ |

```css
.dash-filter { margin:0 0 10px; gap:3px; flex-wrap:nowrap; overflow-x:auto; … }
/* 6개를 320px 한 줄에 넣는다 (R3-1). 가용 폭은 320 − #app 12×2 − .dash-ctl 14×2 = 268px 이고
   합계는 글자 187 + 패딩 60 + 간격 10 = 257px 이다. 이 선택자 안으로만 줄인다 —
   .tab 은 메인 내비게이션과 공유하는 클래스라 밖으로 새면 내비 탭까지 작아진다 (R3-3).
   가로 스크롤 폴백과 scrollPresetIntoView() 는 지운 게 아니라 남겨둔 안전망이다 (R3-4) —
   글자를 키운 사용자나 앞으로 늘어날 라벨이 여기에 걸린다.
   min-height:44px 은 .tab 본체가 주므로 탭 영역은 그대로 44px 이다 (R3-6, WCAG 2.5.8). */
.dash-filter .tab { flex:0 0 auto; padding:9px 7px; font-size:12px; white-space:nowrap; }
@media (max-width:360px){
  .dash-filter { gap:2px; }
  .dash-filter .tab { padding-left:5px; padding-right:5px; }
}
```

**특이도 버그가 여기서 함께 사라진다 (R13-3).** 330px에서 `.tab { font-size:12px }`(0-1-0)는 `.dash-filter .tab { font-size:13px }`(0-2-0)에 져서 프리셋 칩만 13px로 남아 있었다. 이제 `.dash-filter .tab`이 12px이므로 두 값이 같아져 버그가 성립하지 않는다.

**라벨 축약 (R2-9, R3-9).**

```js
const DASH_PRESETS=[["이번주","week"],["지난달","lastmon"],["이번달","month"],
                    ["3개월","q3"],["올해","year"],["작년","lastyear"]];
```

`3개월` 칩에는 무슨 기간인지 알 수 있는 수단을 준다. 접근성 이름은 보이는 라벨을 포함해야 하므로(WCAG 2.5.3 Label in Name) `3개월`을 앞에 둔다.

```html
<button class="tab …" title="3개월 — 이번 달 포함 최근 3개월" aria-label="3개월 — 이번 달 포함 최근 3개월">3개월</button>
```

`role="group"` · `aria-label="기간 선택"` 구조와 선택 상태 표시는 그대로다(R3-10). 색은 안 바꾸므로 대비도 그대로 유지된다 — `.tab` 글자 `--sub`(#6f6253) · `.tab.on` `--brand`(#6f4e37), 배경은 `.dash-filter`가 놓인 `--card`(#fff)와 `.tab.on`의 `#fff`로 각각 5.27:1 · 7.36:1이라 AA(4.5:1)를 넘는다(R3-7).

# B. 손가락 룰렛 (R4~R5)

## B.1 인원 불일치를 진행 전에 한 번 묻는다 (R4)

**핵심 판정은 `refresh()` 안에 있고, 우선순위는 세 단계다.**

```
1) pts.size < 2            → 기존 "두 개 이상 올려주세요" (R4-10, 불일치 문구보다 우선)
2) pts.size ≠ 참가자 수      → 불일치 질문. settleT·countdown 둘 다 걸지 않는다 (R4-2)
3) 그 외                    → 지금과 정확히 동일. SETTLE(900ms) → 3·2·1 800ms (R4-8)
```

참가자 수는 게임 시작 시점 스냅샷이 아니라 **그 순간의 `gamePlayers().length`**를 읽는다(R4-1). `renderWho()`가 같은 이유로 이미 그렇게 하고 있다.

**승인 상태는 불리언이 아니라 "승인 당시의 손가락 수"로 들고 있는다.**

```js
let okAt = null;   // [이대로 시작] 을 누른 순간의 pts.size. 손가락 수가 바뀌면 승인이 무효다 (R4-9)
```

`refresh()`에서 `okAt === pts.size`일 때만 불일치를 건너뛴다. 손가락이 하나라도 늘거나 줄면 `okAt`이 현재 수와 달라져 자동으로 무효가 된다 — 별도의 초기화 코드가 필요 없고, 지우는 자리를 빠뜨릴 수도 없다.

**문구는 방향에 따라 갈린다 (R4-4, R4-5). 두 수를 모두 보여준다 (R4-3).**

| 조건 | 문구 |
| --- | --- |
| `pts.size < 참가자` | `손가락 3개 · 참가자 5명` / `아직 안 올린 분이 있어요?` |
| `pts.size > 참가자` | `손가락 6개 · 참가자 5명` / `한 분이 두 개 올렸거나, 참가자가 아닌 분이 올렸을 수 있어요` |

두 경우 모두 그 안내 안에 `[이대로 시작]` 버튼이 있다(R4-6). 브라우저 `confirm()`은 쓰지 않는다(R4-7).

**재평가 시점을 코드에 명시한다 (R4-11).** 명단은 폴링으로 바뀔 수 있는데 그때 손가락은 그대로일 수 있다. 감시자를 새로 걸지 않고 **이미 도는 타이머 위에서 다시 본다.**

```js
// 불일치를 다시 보는 지점은 세 곳이다. 감시자를 따로 걸지 않는 이유는 판정이 필요한 순간이
// 이 셋뿐이기 때문이다.
//   ① refresh()        — 손가락이 늘거나 줄 때
//   ② countdown() 진입   — SETTLE 이 끝나 세기 직전
//   ③ 3·2·1 매 틱       — 세는 동안 폴링으로 참가자가 바뀌는 경우. 이미 도는 타이머 위에서
//                        보므로 비용이 없고, 카운트다운을 소리 없이 방치하지 않는다.
```

세 지점 모두 `picked === true`면 아무 일도 하지 않는다(R4-12).

**스크린리더 (R4-13, R4-14).** `#fpMid`에 `role="status" aria-live="polite"`를 준다. `pointermove`는 점의 `left/top`만 바꾸고 `#fpMid`의 내용은 건드리지 않으므로 손가락이 움직여도 리전이 갱신되지 않는다(R4-14). 불일치 안내와 3·2·1은 `#fpMid`의 내용 교체라 그대로 읽힌다(R4-13).

## B.2 가운데 멘트가 손가락에 묻히지 않는다 (R5)

# C. 돌림판 (R6)

## C.1 왜 정적인 값으로는 못 고치는가

기호를 정하자. `A(t)` = 판의 회전, `L(t)` = 라벨 글리프의 역회전, 승자 조각의 중심각 `mid`.

- 멈춘 순간 이름이 똑바로: `A(end) + L(end) ≡ 0 (mod 360)`
- 멈춘 순간 승자가 핀 아래: `mid + A(end) ≡ 0 (mod 360)`

두 식에서 `L(end) ≡ mid`다. 시작 상태에서 관찰자가 보는 것은 조각 배치(각 조각이 어디 있는지)와 `L(0)`뿐인데, 조각 배치는 `A(0)=0`이라 그대로 드러나 있으므로 **감출 수 있는 정보는 `A(end) mod 360` 하나**다. `L`이 상수면 `L(0) = L(end) ≡ mid`가 되어 그 값이 그대로 새어 나간다 — 이것이 현재 버그다.

조각 배치를 통째로 돌리는 상수 `B`를 넣어도 같다. `B`는 시작 상태에서 눈에 보이므로 관찰자의 정보가 늘 뿐이다. 즉 **`L`은 시간에 따라 변해야 한다.** 정적인 어떤 값으로도 R6-1과 R6-3을 동시에 만족시킬 수 없다.

따라서 설계는 이렇게 된다.

```
L(0)   = 0        ← wi 와 무관 · jitter 와 무관 · n 이 같으면 매 판 동일 (R6-1, R6-2)
L(end) = −spin    ← A(end) + L(end) = 0 → 멈춘 순간 똑바로 (R6-3)
```

`L`을 판과 같은 시간·같은 이징으로 보간하면 글리프의 절대 각도가 **처음부터 끝까지 0**으로 유지된다. 조각은 돌고 이름은 서지 않는 관람차 모양이다. 5바퀴를 4.2초에 도는 동안 이름은 어차피 흐름이고, 감속 구간에서 기울지 않은 채로 자리를 잡는다.

## C.2 순수 함수 (R6-7)

게임 마커 블록(1565행)에 넣는다.

```js
// 돌림판의 회전량과 라벨 각도. 난수는 인자로만 받는다 — 시작 시점 라벨 각도가 wi 와 무관함을
// 결정론적으로 검증할 수 있어야 하고, 그게 이 함수를 따로 뺀 이유다 (R6-7).
// labelStart 가 0 인 것이 이 설계의 전부다: 정지 상태에서 기울기가 상수면 거기서 샐 것이 없다.
function wheelSpin(n, wi, rnd){
  const a = 360 / n;
  const mid = (wi + 0.5) * a;
  const jitter = ((rnd || Math.random)() - 0.5) * Math.max(0, a - 10);
  const spin = 360 * 5 - mid + jitter;
  return { a, spin, labelStart: 0, labelEnd: -spin };
}
```

테스트는 `n ∈ {2, 3, 5, 10, 11, 24}` 전부에 대해 모든 `wi`에서 `labelStart === 0`임(R6-8)과 `((spin + labelEnd) % 360 + 360) % 360 === 0`임(R6-9)을 확인한다.

## C.3 라벨을 어떻게 돌릴 것인가

회전 중심은 **각 라벨 자신**이어야 한다. `<g>` 하나를 SVG 중심 기준으로 돌리면 라벨이 조각을 벗어나 역방향으로 궤도를 돈다(요구사항의 설계 참고).

SVG `<text>`에 CSS `transform`을 걸고 `transform-box: fill-box; transform-origin: center`로 **글자 자신의 바운딩 박스 중심**을 축으로 삼는다. 현재 속성이 쓰는 축은 앵커 `(x, y)`이고 fill-box 중심은 `(x, y+4−0.35·fs)`라 1 사용자 단위 미만 차이 — 화면에서 구분되지 않는다.

```css
/* 라벨 역회전은 시간에 따라 변해야 한다 (설계 C.1). 회전축이 글자 자신이어야 하므로
   transform-box:fill-box 가 필요하다 — 기본값(view-box)은 축이 viewBox 좌상단이라
   라벨이 판 밖으로 날아간다.
   @supports 로 감싸는 이유는 미지원 브라우저에서 이 규칙이 살아 있으면 축이 틀린 채로
   돌기 때문이다. 그 경로의 누출 차단은 JS 폴백이 맡는다(아래). */
@supports (transform-box: fill-box) {
  .wlab { transform-box:fill-box; transform-origin:center; transform:rotate(0deg); }
}
```

**폴백에서도 누출을 막는다.** 미지원 브라우저에 예전 동작(정지 상태에 `rotate(-spin)` 을 박아 두기)을 남기면 P0 결함이 그대로 살아 있는 셈이다. 대신 **역회전 값을 마크업에 박지 않고 `data-rot` 에만 실어 두고, 회전이 한창일 때 속성으로 한 번에 넣는다.**

| 시점 | 라벨 각도 | 글자의 절대 각도 |
| --- | --- | --- |
| 정지 (t=0) | `rotate(0)` — **`wi` 와 무관** | 0 (똑바로) |
| 0 ~ 350ms | `rotate(0)` | 판과 함께 돈다 (판에 그려진 것처럼) |
| 350ms (교체) | `rotate(labelEnd)` | 값이 튀지만 그 구간의 각속도가 1,000°/s를 넘어 반지름 62 기준 프레임당 18px 이동이라 눈에 안 띈다 |
| 350ms ~ 끝 | `rotate(labelEnd)` | 판과 함께 0 으로 수렴 — 멈출 때 튀지 않는다 |

`lessMotion()` 이면 판이 이미 끝값으로 뛴 뒤이므로 **같은 프레임에** 교체한다. 기다리면 글자만 기울어 있는 프레임이 생긴다.

남는 한계: 개발자 도구로 DOM 을 열면 `data-rot` 에서 답을 읽을 수 있다. 다만 이 앱은 당첨자를 클라이언트에서 먼저 뽑으므로(`gamePickWinner`) JS 메모리·사다리 경로·예약된 `showGameResult(winner)` 어디서든 같은 정보가 나온다 — 이번 스펙이 막는 것은 **화면만 보고 산수로 알아내는 것**이다.

`playWheel`의 배선은 판과 **같은 처방·같은 리플로우**를 공유한다(R6-10 유지).

```js
const { a, spin, labelEnd } = wheelSpin(n, wi, Math.random);
…
// 속성은 미지원 브라우저용 폴백으로 남긴다. 지원 브라우저에서는 위 CSS 규칙이 이 속성을 덮는다
// (transform 표현 속성은 작성자 스타일시트 규칙에 진다).
`<text class="wlab" transform="rotate(${labelEnd} ${x} ${y})" …>`
…
rot.style.transition = "none";
rot.style.transform  = "rotate(0deg)";
void $gv().offsetHeight;              // 시작값 커밋 — 판과 라벨을 같은 리플로우 하나로 묶는다
if(slow){
  rot.style.transition = "transform 4.2s cubic-bezier(.16,.72,.14,1)";
  if(labelsAnimate) labs.forEach(el=> el.style.transition = "transform 4.2s cubic-bezier(.16,.72,.14,1)");
}
rot.style.transform = "rotate(" + spin.toFixed(2) + "deg)";
if(labelsAnimate) labs.forEach(el=> el.style.transform = "rotate(" + labelEnd.toFixed(2) + "deg)");
```

`labelsAnimate = !!(window.CSS && CSS.supports && CSS.supports("transform-box","fill-box"))`. 거짓이면 인라인 `transform`을 아예 손대지 않아 속성 폴백이 그대로 산다.

**`lessMotion()`일 때 (R6-5).** 전역 reduced-motion 블록이 모든 `transition-duration`을 `.01ms !important`로 끄므로 판과 라벨이 같은 프레임에 끝값으로 점프한다. 절대 각도는 계속 0이고, 화면에 남는 시작 상태는 `labelStart = 0`이라 새는 것이 없다.

핀 아래 조각이 승자와 일치하는 불변식(R6-6), `gcolor(i, n)`과 범례(R6-11), 번호 라벨 경로(R6-4)는 모두 그대로다 — 번호도 같은 `.wlab`을 쓴다.

## F.6 받아들인 비대칭 (R12-18, 알려진 한계)

`dashStatsHtml()`의 주문 KPI는 **전원 기준**(`countDrinks()`와 같은 수)이고 `다른 분들` 목록은 **나를 뺀 n−1행**이다. KPI를 나 제외로 바꾸면 닫힌 화면의 집계와 어긋나므로 바꾸지 않는다. 완화 수단은 카드 제목 `다른 분들`이다 — 목록이 나를 세지 않는다는 사실을 제목이 말한다. 탭 라벨에서 사라진 `n잔`은 이 KPI가 대신한다(R12-18).

**`line-height` (R13-17).** `.stat .num`(24px)과 `.game-win .wn`(25px)이 `body`의 1.5를 상속해 줄 상자가 36px · 37.5px가 된다. 사촌인 `.cc-n`(23px/1.1) · `.kpi .n`(17px/1.1)과 맞춰 **1.1**을 준다. 눈에 보이는 높이 감소라 QA 케이스를 단다.
